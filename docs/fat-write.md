# FAT12/16/32 (vfat, Linux fs/fat) の書き込み — 実験的

2026-11-13。読み取り専用で動いていた `fs/fat` (**無改変**。`third_party/fat` に差分なし) を、ext2 / exFAT の書き込みで作った LinuxCompat の書き込み基盤の上で書き込み可能にした。
`USBMEM_NTFS_WRITE` を付けたビルドだけで有効 (CMake `-DUSBMEM_NTFS_WRITE=ON` / Gradle `-PusbmemNtfsWrite=true`)。無効なビルドで `read_only = 0` を要求すると `-EROFS`。実行時にも `mount_rw` (`read_only=0`) が必要。
**既定のビルドは今までどおり読み取り専用**。実機 (USB ディスク) での確認はまだ (ホストと AVD のみ。実機には触れていない)。

## 先に結論
- 作成・書き込み (拡張・上書き・隙間を作る書き込み)・truncate (縮小・拡張)・削除・rmdir・rename (同一ディレクトリ・跨ぎ・上書き・ディレクトリ・大文字小文字だけの変更) が動く。
  FAT12 / FAT16 / FAT32、クラスタ 512B〜64KiB、論理セクタ 512 / 4096 (4Kn)、パーティションのオフセット付きで確認。長い名前 (LFN: 最長 255 文字、日本語、サロゲートペアの絵文字) と 8.3 名の衝突 (`LONGNA~1`…) も扱う。
- 検証は**独立実装**で行った: dosfstools の `fsck.fat -n` (FAT1 / FAT2 の一致・FSInfo・連鎖・重複名・LFN のチェックサムを含む)、mtools (`mcopy`)、7-Zip。自前ドライバで書いたイメージが `fsck.fat -n` で clean、
  かつ同じ操作を**ホストのディレクトリ**に POSIX 操作で行った結果と、ツリー全体 (種別・サイズ・sha256) が一致。Linux カーネルの vfat との相互検証 (`mount -t vfat`、両方向、fsck なし) は CI で行う (`tools/run_fat_kernel_tests.sh`。ローカルは root が要るので使わない)。
- FAT にジャーナルは無い。順序で安全を作る: **ダーティ印 (ブートセクタ + FAT16/32 は FAT[1]) を最初の変更の前に確定** → データ → FAT (FAT1 → flush → FAT2 → flush) → ディレクトリエントリ。削除はエントリ → FAT。
  電源断・抜去のあとはボリュームが「汚れた」状態で残り、`fsck.fat` が必要。**アプリは汚れたボリュームを書き込み可でマウントしない** (読み取り専用に落ちる)。これは仕様。
- 電源断の模擬・突然変異テスト・ファジング (ASan/UBSan) の結果は下の「結果」。
- `symlink` / `link` / `readlink` は FAT に存在しない (`-95`)。4GiB-1 を超えるファイルは `EFBIG`。

## 構成 (どこに何があるか)
書き込み基盤は ext2 / exFAT のものを共用する。FAT 固有なのは `rt_vfs_fat.c` (書き込みは `#ifdef USBMEM_NTFS_WRITE`)、`fat_volume.cpp`、`fat_c.h`。この作業で基盤に足した/直したもの (共有ファイルは追加のみ・最小):

| 場所 | 内容 |
|---|---|
| `rt_bh.c` | `mark_buffer_dirty` が bd の dirty フック (`usbmem_dirty_hook_`) を呼ぶ (ディレクトリ領域の dirty 順を記録する)。**`iunique` が 2 を返さない**ようにした (後述) |
| `rt_buffer.c` | `__block_write_begin` が `len == 0` を許す (FAT の拡張 truncate = `fat_cont_expand_simple` が呼ぶ)。`cont_write_begin` / 拡張時のゼロ埋め |
| `rt_pagecache.c` | `usbmem_bdev_dirty_ranges` / `usbmem_bdev_writeback_ranges` (exFAT と共用) の 512B 単位の dirty 範囲の扱い |
| `include/compat/fs.h` | `block_device` の dirty フック、`super_block` の FAT 用フラグ |
| `rt_vfs_fat.c` | ホスト入口。書き込み操作・ピン表・同期の順序・ダーティ印・クリーン unmount |
| `fat_volume.cpp` / `fat_c.h` / `fat_volume.h` | `FatVolume::mount_rw`、`create / mkdir / unlink / rmdir / rename / write / truncate`、`writable()` |

### `iunique` と FSInfo の予約番号 (重要な落とし穴)
`fat_write_inode` は **`i_ino == MSDOS_FSINFO_INO (2)` を FSInfo の書き出し**とみなす。LinuxCompat の `iunique` は最初の割り当てが 2 になりうる (カーネルは起動後のカウンタが大きいので当たらない) ため、
ボリュームで最初に作られた通常の inode が ino 2 を得ると、その inode のディレクトリエントリ (サイズ・開始クラスタ) が**書かれない**。FAT のデータは書かれ FAT の連鎖もできるのにエントリが 0 バイトのまま、という壊れ方をする
(`fsck.fat` が「未使用クラスタ」と報告して発覚した)。`iunique` が 2 を飛ばすようにして直した (`tools/run_fat_write_tests.sh` の短い操作列でも再現・回帰確認済み)。

### 書き込み可でマウントする条件 (`writable_precheck`)
次のどれかなら**読み取り専用に落ちる** (`writable() == false`、書き込みは `-EROFS`/30)。イメージは 1 バイトも変えない (`--refuse` テストで確認)。
- ブートセクタの状態バイト (FAT12/16: 0x25、FAT32: 0x41) のダーティビット (bit0) または MediaFailure (bit1)。
- FAT16/32 で FAT[1] のクリーン bit (FAT16: bit15、FAT32: bit27) が落ちている。**どの面の FAT も**見る (Linux は 1 面目しか見ないが、2 面目だけ落ちている = 更新の途中で止まった状態)。FAT12 にはこの bit が無い。
- FAT の面の数が 1 または 2 でない。上流のマウント自体が失敗するもの (不正なブートセクタ、FAT32 のバージョン違いなど) はマウントしない。
常に**読み取り専用でマウント**する。最初の書き込みの直前に `SB_RDONLY` を外してダーティ印を確定する。マウントしただけ・読んだだけでは何も書かない (`--noop` テストで、rw を要求して書かずに閉じたイメージが**バイト一致**)。

### ダーティ印と FSInfo
最初の書き込み操作 (`begin_op`) で、他のどのバイトを変えるより前に次を確定する (それぞれ書いて flush):
1. ブートセクタのダーティビット (`fat_set_state`)。
2. FAT16/32: 全ての FAT 面の FAT[1] のクリーン bit を落とす。
3. FAT32: FSInfo の空きクラスタ数・次の割り当て位置を「不明」(0xFFFFFFFF) にする (書き込み中に落ちても古い数を信じさせない)。
クリーンな unmount の最後: FAT32 は空きクラスタ数を数え直して FSInfo を書く (`max_cluster` が 16M クラスタを超えるボリュームは「不明」のまま。`fat_count_free_clusters` が重いので) → flush → FAT[1] のクリーン bit を戻す → ブートセクタのダーティビットを `fat_put_super` が消す。
書き込みが失敗した/同期できなかったときは、ダーティ印を戻さない。

## 同期の順序と安全の規則
`usbmem_fat_sync` (`sync_all`) の手順:

1. **データ**: 各ファイルの page cache をデバイスへ書き、flush。ここで途切れても、どのファイルのメタデータもまだ変わっていない (新しいクラスタは FAT でまだ「空き」)。
2. **inode メタデータ**: `write_inode` でディレクトリエントリを更新 (bd の dirty になるだけ。inode ごとに別の「操作」として記録)。
3. **メタデータを種類別の順序で**。各段階の間に flush を入れる (順序を守らない USB キャッシュでも成り立つように)。
   - **確保系** (作成・書き込み・拡張・mkdir・名前の追加): 新クラスタの中身 (新しいディレクトリのゼロ埋めなど) → **FAT1 → flush → FAT2 → flush** → ディレクトリエントリ (dirty になった順。同じ操作の中の複数セクタ = 長い名前のスロット → 短い名前の順は、間に flush)
   - **解放系** (削除・rmdir・縮小・上書き rename): ディレクトリエントリ → FAT1 → FAT2
4. **確保系と解放系を同じ同期の中で混ぜない**。操作の入口 (`begin_op`) で種類が変わるときは先に同期する。

理由と、それぞれの規則を外すと何が起きるか (突然変異テストで確認。「テスト」参照):
- **ダーティ印は最初の変更より前に確定**: 外すと、電源断のあとボリュームが clean に見えるのに中身が変わっている (B)。
- **解放したクラスタを同期の前に再利用しない** (種類切り替えでの同期): 外すと、解放したクラスタに新しいデータが先に書かれ、電源断のあと「まだ生きている古いファイル」の内容が新しいデータに入れ替わる (A)。
- **データ → FAT → エントリ**: エントリ (ファイルの存在・サイズ・開始クラスタ) が最後。エントリが先だと、電源断のあと「存在するのに中身が無い」ファイルや、別のファイルとクロスリンクしたファイルが現れる。
- **FAT1 を FAT2 より先に**: 電源断のあと 2 面が食い違っても `fsck.fat` は「どちらも intact」として最初の面を採る。逆順だと古い面を採る可能性がある。
- **削除はエントリが先、FAT が後**: 先に FAT を解放すると、エントリがまだ解放済みクラスタを指す (別ファイルに再利用されるとクロスリンク)。
- **長い名前のスロット → 短い名前の順**: 短い名前のエントリ (実体) が先に見えて長い名前のスロットが欠けると、名前が壊れて見える (LFN のチェックサム不一致で `~1` 名に化ける)。

### 段階境界 (rename とディレクトリ拡張) — 全書き込み位置の電源断テスト (dense) で見つかった 2 件
ディレクトリのセクタは 512B 単位で書かれるので、1 つのセクタに「同じ操作の中の順序が逆の変更」が同居すると、セクタ単位の順序づけでは守れない。上流の `fs/fat` は無改変のまま、
呼び出しを CMake の `-D` で差し替え (`fat_remove_entries` → `usbmem_fat_remove_entries`、`dir.c` の `fat_chain_add` → `usbmem_fat_chain_add`。`src/rt_vfs_fat.c`) て、そこで途中までを確定する:
1. **rename**: 「新しい名前を追加 → 古い名前を削除」。新しい名前の長い名前スロットの後ろと、古い名前の先頭スロットが同じセクタに入ることがある。そのセクタは追加 (確保系) と削除 (解放系) の両方を含むので、
   古い名前の短い名前の削除 (別のセクタ) より先に古い名前の先頭スロットの削除が届き、電源断のあと「長い名前を失った短い名前」(`DENSE_~7.TXT`) が現れた。古い名前を削除する前に、ここまで (新しい名前) を確定する。
   その間の電源断で残るのは「同じ実体を指す名前が 2 つ」(`fsck.fat`: share clusters。Linux の vfat も同じ。FAT の rename は原子的でない) だけ。
2. **ディレクトリの拡張**: 末尾の空きスロットに長い名前の前半を書き、新しいクラスタに残り (長い名前の最後のスロット + 短い名前) を書き、最後にクラスタをつなぐ (FAT)。つなぎが先に届くと、新しいクラスタの短い名前が
   前半のないまま見える。つなぐ前に、ここまで (新クラスタの中身 → FAT → ディレクトリ。まだつながっていないので見えない) を確定する。

### 電源断の途中で FAT の複数セクタが中途半端に書かれる件
FAT の更新は複数セクタにまたがりうる (特に FAT12 はエントリが 1.5 バイトでセクタ境界にまたがる)。FAT1 を昇順に書く途中で電源が切れると、**既存ファイルの最後のクラスタから新しいクラスタへのリンクだけが先に残り、
リンク先の FAT エントリはまだ空き**という状態があり得る (そのファイルのエントリはまだ古いサイズのまま)。`fsck.fat` は "Contains a free cluster. Assuming EOF." と報告して連鎖を切る。元のデータには影響しない。
FAT の仕様上、複数セクタの更新は原子的でなく、ここでは軽減していない (テストはこれだけを許容し、サイズと連鎖の矛盾・クロスリンクなどは許容しない)。7-Zip は連鎖が長さに合わないイメージ全体を拒否することがあるので、その場合の修復前の読み出しは mtools で行う。

### ピン (ino → inode の表)
FAT の ino は `iunique` で実行時に採番され、ディスク上の値ではない。`lookup` / `readdir` / `create` が返した inode を**参照を保持**して ino から引く (`unmount` まで有効)。
削除・rmdir・rename で上書きされたものはピンを外す (これで inode が追い出され、`fat_evict_inode` がクラスタを解放する)。ピンには**親の ino** を持たせ、ディレクトリを自分の中へ移す rename (`-EINVAL`) の検査に使う。

### 大文字小文字・名前
- FAT の名前は大文字小文字を区別しない (lookup も重複判定も)。LinuxCompat の既定 NLS (utf8) は **ASCII の大文字小文字だけ**を同一視する (起動時の警告 "utf8 is not a recommended IO charset ... case sensitive!" は無害。非 ASCII の大文字小文字、例えば `É` と `é` は別の名前として扱う)。
- 作った名前の綴りはそのまま残る (`Hello.TXT`)。大文字小文字だけが違う名前への rename は、一時名 (`.usbmem-ren-<ino>-<n>`) を経由して 2 回の rename として実行する (新しい名前の lookup が元のファイル自身に当たるので、綴りだけを変える経路を上流に任せず、確実な「別名への移動」に分解した)。途中で止まっても元のファイルは失われない (一時名で残る)。
- UTF-16 で 255 文字まで (日本語 255 文字、サロゲートペアの絵文字は 127 個まで = 254 単位。128 個は `ENAMETOOLONG`)。不正な UTF-8 は `EINVAL`、`\ : * ? " < > |`・制御文字・末尾のスペースは `EINVAL` (末尾のピリオドは上流が黙って落とす)。
- 8.3 名の衝突は上流の規則 (`LONGNA~1` … ハッシュ付き) で解決する。同じ 6 文字の先頭を持つ長い名前を大量に作ると、上流の実装自体が O(N²) になる (ディレクトリ全走査 × 候補数)。通常の利用では問題にならない。
- ディレクトリは 2MiB (65536 エントリ) まで。FAT12/16 のルートは固定長 (`root_entries`) で、満杯になると `ENOSPC`。

### サイズの上限
FAT のファイルサイズは 32 ビット。4GiB-1 (0xFFFFFFFF) を超える位置への書き込み・truncate は `EFBIG` で、何も変えず、そのファイルは使い続けられる (`--limits`)。

- (E) 修復前の読み出し: 元のファイルが元のまま読める。
- (F) 修復前に読み出した各ファイルに、空きクラスタの目印 (元のボリュームの空きを `tools/fat_fill_free.py` で 0xEE に埋めてある) が見えない = 書かれていない新しいクラスタの中身がファイルの一部として見えていない (「データが先」の検査。mkfs の空きは 0 なので、目印がないと検出できない)。
- (G) 修復前のツリーの名前が、操作列に現れる名前か元からある名前のどれかである (長い名前を失った短い名前 `VERY_L~1.TXT` が見えない)。`tools/fat_crash_check.py`。
- 2 つの操作列: `main` (サンプリング。順序保持・キャッシュ × 途中切断あり/なし × 同期方式 2 通り) と `dense` (短い操作列を**全ての書き込み位置**で止める。ディレクトリの拡張・長い名前のスロット列がセクタ境界をまたぐ追加・改名・削除)。
  サンプリングだけでは書き込み順序の 1 ステップの違いを取りこぼす (突然変異 `NO_DIRGROW_BOUNDARY` / `NO_RENAME_BOUNDARY` / `NO_NEWCLU_FIRST` / `LOG_REVERSE` はサンプリングでは検出されなかった)。
- (D) が許容する指摘に、孤立した長い名前スロット (`Orphaned long file name part`: 追加の途中で短い名前より先に長い名前のスロットが届いた、または削除の途中で短い名前だけ先に消えた。短い名前の削除は長い名前より先。見えるファイルはない) と、
  rename の途中の「同じ実体を指す名前が 2 つ」(share clusters とそれに続く切り詰め) がある。後者は `fat_crash_check.py fsckfilter` が組として取り除く (実体は残り、元のファイルの内容は (A)(E)、露出は (F) が見る)。

突然変異テスト (`-DCMAKE_C_FLAGS=-DUSBMEM_MUTATE_...` の別ビルド。通常ビルドには入らない):
| 突然変異 | 外す規則 |
|---|---|
| `USBMEM_MUTATE_NO_DIRTY` | ダーティ印を書かない |
| `USBMEM_MUTATE_NO_KIND_SYNC` | 確保系/解放系の切り替えで同期しない |
| `USBMEM_MUTATE_ORDER` | メタデータの書き込み順序を逆にする (確保系と解放系を入れ替え) |
| `USBMEM_MUTATE_NO_NEWCLU_FIRST` | 新クラスタの中身を先に書く規則を外す |
| `USBMEM_MUTATE_NO_DATA_FIRST` | データをメタデータの後に書く (書き込みごとのデータの書き出しも止める) |
| `USBMEM_MUTATE_NO_RENAME_BOUNDARY` | rename の「新しい名前 → 古い名前の削除」の間の段階境界を外す |
| `USBMEM_MUTATE_NO_DIRGROW_BOUNDARY` | ディレクトリ拡張でクラスタをつなぐ前の段階境界を外す |
| `USBMEM_MUTATE_LOG_REVERSE` | ディレクトリセクタを逆順に書き、同じ操作の中の flush も挟まない |

## 既知の限界・未実装
- **実機 (USB ディスク) では未確認**。ホスト (ASan/UBSan を含む 4 構成) と AVD のみ。手順は `docs/fat-port.md` の末尾。
- 電源断の模擬の限界: 書き込みが途中で切れる単位は 512B のセクタ。実デバイスの挙動 (キャッシュの順序、書き込みの原子性、FUA/flush の尊重) は模擬しきれない。flush を無視する安価な USB ブリッジでは順序の保証が効かない。
- 複数セクタにまたがる更新 (FAT の更新、長い名前のスロットがセクタ境界をまたぐ場合) の途中で電源が切れると、そのファイル 1 件が壊れうる。`fsck.fat` が直す。FAT の仕様上の弱点で、ここでは軽減していない。
- 電源断のあと、未参照クラスタは `fsck.fat` が回収するまで残る (容量が減って見える)。
- FSInfo の空きクラスタ数: 16M クラスタを超える FAT32 ボリュームではクリーン unmount 後も「不明」(0xFFFFFFFF) のまま (他の実装は読み込み時に数え直すので問題ない)。
- 短い名前の codepage は 437 (cp932 の表は登録済みだが、マウントオプションを渡す口が未実装)。非 ASCII の短い名前 (8.3) は、長い名前を持つ形で作るので表示には影響しない。
- 非 ASCII の大文字小文字の同一視はしない (ASCII のみ。上の「大文字小文字・名前」)。Windows とは `É` / `é` の扱いが違う。
- exFAT の `bm_snap` のような全体走査はないが、確保系の同期ごとに FAT の dirty な範囲を比べて新クラスタを見つける (FAT12 は FAT 全体 = 最大 6KiB を比べる)。
- UI の書き込み許可 (`WriteMode`) は他の FS と同じ (`UsbScreen.kt` の書き込み可能な FS のリストに fat12/fat16/fat32 を追加)。

## 結果 (2026-11-13、ホスト = Linux x86_64 / AVD = API 37 x86_64。**実機・カーネル vfat は未実施**)
